Two disclosure harnesses, and what each one is for

They are not equivalent and not redundant. They ask different questions, they disagree on this skill, and the disagreement is explainable. Everything below is a single run at small n — read direction, not decimals.

Which one answers what

skill-creator optimize-disclosure.ts

“Is this layout cheap, and does it still work?”

  • Measures context tokens per run — real cost
  • Per-file pull rate → verdict: inline / prune / signpost / keep
  • Distinguishes prune from signpost: unread-and-pointed-at vs unread-and-unnamed
  • Proposes and measures restructured layouts
  • Held-out split; pass-rate guardrail blocks cheaper-but-broken
  • Knows load modes: a scripts/ file should pull 0%

this repo, composition-runner.ts --arm disclosed

“Does the right file open at the right moment?”

  • Per-scenario expected references → recall and precision
  • Measures abstention: did it correctly decline to ask?
  • Runs a deterministic linter on the produced call
  • Three arms: no skill / injected / on-disk
  • No cost metric at all — the real gap

Use theirs to decide the layout. Use this one to check the behaviour. Pull rate cannot tell you whether the right file opened for a given situation, and per-scenario recall cannot tell you what a run cost. Neither subsumes the other.

The inline verdicts collide with the size budget, and that tension is the real finding.

Those three files are 10,838 tokens. Inlining them into a 4,657-token body gives ~15,500 — three times the specification's 5,000 recommendation. When a 5k-token file is pulled every single time, the honest reading is not “move it into the body.” It is this skill needs 15k of content and no layout makes that cheap. The fix is shrinking what is there, not relocating it.

This repo — what it found

15 scenarios, 1 run each · the agent is told the skill exists and decides for itself whether to open anything

Its unit is the scenario, not the file. It does not ask “how often was this file pulled?” — it asks “for this situation, did the file that situation needed get opened, and was anything opened that was not needed?” Those are recall and precision, and they have no per-file equivalent, which is why this table looks nothing like the one above.

Why the two sections do not line up

They are measured through different doors, on purpose. skill-creator names the skill in the prompt, so every run definitely loads it and does the work — that is what makes its numbers about layout rather than routing. This repo lets the agent decide, so a third of its runs are scenarios where declining to ask and reading nothing is the correct answer.

And the units differ. A pull rate is per file across all runs. Recall and precision are per scenario against a labelled expectation. There is no arithmetic that converts one into the other, so a file showing 100% in the first table and 13% in this repo's runs is not a contradiction: the first counts runs that all did the work, the second counts runs that mostly should not have.

An earlier draft of this page put both as adjacent bars in one table. That was wrong — side-by-side bars are an instruction to compare, and it manufactured a discrepancy the data does not contain.

--num-workers defaults to 4 and is the free speedup — it costs nothing in what is measured. Past about 10 concurrent runs the connection saturates and every run fails at once.

Single runs at small n throughout. skill-creator baseline: 6 scenarios x 2 runs, train split of 4, killed after the baseline sweep when the extraction-proposal call stalled. This repo: 15 scenarios x 1 run. Repeat runs of identical code have varied by plus or minus 10 points on these rates, so treat any single figure as indicative of direction only. Verdict colours are the status palette (warning / critical / good). Every bar carries its number, because the light steps used here sit below 3:1 against this surface. The two sections are deliberately not plotted together: their units differ and adjacency would imply a comparison the data does not support.
