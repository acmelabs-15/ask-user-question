# Ask-user-question — research proposal

Status: direction and host scope approved with review refinements. Not implemented. Research date: 2026-09-11. Selected hosts: Claude Code, Codex, and Gemini.

Peter defines the desired experience. Research supplies concepts we can turn into instructions and evaluate. Keep one integrated question-and-reply skill: flow determines the next action; language and visual organization make each exchange understandable. These three concerns are not proposed as three separate skills.

Peter also wants agents to reach for this guidance automatically during relevant work. Selection is part of the requirement, not an installation detail to assume. Measure whether it loads without being named, then measure whether the exchange follows it. An explicit instruction from another skill to load it, or good behavior without a load, does not demonstrate automatic selection.

The useful foundation is **shared understanding sufficient for the next step**. Clark and Brennan's account treats understanding as something participants establish together for their current purpose. It does not require perfect understanding of the whole project. A relevant reply can supply evidence without a separate confirmation question. Their term “acceptance” concerns understanding a contribution; it is not permission to perform an action. Applying this account to an agent is our design proposal, not a result tested by the chapter. [Clark and Brennan, 1991](https://web.stanford.edu/~clark/1990s/Clark,%20H.H.%20_%20Brennan,%20S.E.%20_Grounding%20in%20communication_%201991.pdf).

## Proposed flow

1. **Identify the missing piece.** State internally what this question needs to settle and which next action depends on it. Check the conversation, project files, and relevant research before asking for an answer the agent can discover. Ask Peter for his intent, priorities, or a consequential choice that remains his. Keep unsupported inputs open; a plausible assumption does not settle them.

   When instructions or evidence disagree, investigate the discrepancy before asking what to do. Understand the relevant API, version, terms, or behavior. Compare the evidence and prepare a concrete resolution. The agent owns choosing that investigative approach and presenting the issue clearly. The user owns any remaining intent or trade-off; the agent must not invent that answer.

   Before asking about a decision, identify how the plausible answers would change the next action and why further inspection cannot settle the difference. An open question remains appropriate when it seeks information only the user can provide. The failure is handing over the agent's preparation work, not open-ended wording by itself.

   A small, reversible implementation choice can remain the agent's when both paths satisfy the agreed behavior. State the choice and reason, then proceed within authorization. This is a visible implementation decision, not an invented requirement or a claim about what Peter wants. Small code size does not excuse silently choosing a product behavior.
2. **Prepare one question.** Supply the context needed to understand that missing piece. Ask about one bounded subject. For a choice, make the outcomes, relevant costs, and recommendation understandable inside the question dialog. Use an open question when the answer space is still being discovered; do not manufacture choices merely to fill option slots.

   Use the actual question tool's supported fields and a supported untimed path. Wait for the user without imposing a response deadline. A delivery acknowledgment or an expired polling interval does not answer or cancel the question. If the host independently closes it, preserve the unresolved decision and explain the limitation.
3. **Read the reply for meaning.** Separate the parts that answer the current question, qualify or correct it, leave gaps, conflict with evidence, or introduce useful future topics. A label, free text, or note is the form of the reply, not its meaning. Check for a request to explain, a change of direction, a refusal, or delegated judgment before treating it as an answer to the original question. A reply can do several of these things at once.
4. **Check the evidence needed for the next action.** Trace each required fact, choice, and constraint to the user's words, inspected project evidence, or a verified research source. Keep an inference distinct from what was directly established. An unverified interpretation remains open and cannot supply a missing input for dependent work. If a required input lacks support, or relevant evidence conflicts, pause the work that depends on it. Name the gap and choose how to resolve it. If the gap has grown, revise its scope explicitly.
5. **Take the action the reply supports.** Use the cases below. Preserve settled facts and constraints. Record the result through the surrounding project's memory workflow, then continue, investigate, or ask again as needed. Preserve useful deferred topics and tell the user what remains for later.

The cases below can apply to different parts of the same reply. The first three and the evidence/conflict/deferred-topic requirements come directly from Peter. The direction-change case also covers his request to research rather than continue asking for expert knowledge.

- **Enough clarity:** Continue with the next authorized step. That step can be code analysis or research; it need not be implementation. An answer need not settle every later question.
- **The user does not understand:** Repair the question. Restore missing context, explain a term, make an option concrete, or separate combined subjects. Choose the repair that addresses the reported problem.
- **The user understands, but information is missing:** Preserve what the reply settles. Identify the particular remaining gap. Investigate it if evidence can answer it; otherwise ask one focused follow-up.
- **The reply changes direction:** Follow the correction, refusal, delegation, or research request within its stated scope. Retire or revise the original question if it no longer applies.
- **Information conflicts with evidence:** Show the specific conflict and its source. Distinguish a suspected error from an established discrepancy. Resolve factual uncertainty through analysis or research where possible; openly challenge an unsupported premise when it requires discussion. Preserve Peter's actual statement instead of silently substituting a preferred interpretation.
- **Useful material belongs later:** First check whether it changes a dependency or constraint on the current decision. If it does, incorporate it now. Otherwise record the topic, its source, why it is deferred, and when or under what condition to revisit it. Mark an undecided revisit condition as open. Tell the user it is preserved. Then return to the particular unresolved point in the current question. Preserve a suggestion as a suggestion; recording it does not authorize starting that work or make the original answer complete.

These requirements do not reduce to a command to ask more questions. Before each follow-up, identify the missing evidence and whether Peter, the code, or research can supply it. The agent must do the analysis needed to ask a useful question; Peter should not have to build the expert model for it.

A proposed record for the current exchange contains: the current question; what the reply settles and its source; retained conditions; remaining gaps; disputed claims and evidence; deferred topics with a revisit condition; and the next supported action. This is a handoff to the project's Markdown memory files, not a new project-management system owned by the skill.

For example, if a question about dismissing an in-app reminder receives an idea for future email reminders, the agent can say: “I recorded email reminders for the later channel discussion. The in-app behavior is still open: should the user be able to dismiss this reminder?” This is an illustrative application, not a quote from Peter or a tested dialog. A newly stated requirement that affects dismissal must be addressed now instead of deferred by convenience.

Silence supplies no evidence of an answer. A recommendation or the tool's default is not a user decision. An expression of understanding is not automatically permission. These are action constraints from the project and tool contract, not conclusions that a conversation study can establish for us.

Research distinguishes clarification of prior meaning from information-seeking follow-up. That supports different instructions for the second and third cases. A study of language models also found that prompting more such conversational acts did not improve their agreement with the human turns being modeled. The lesson for this proposal is to evaluate **which action fits**, not reward the number of questions. The study uses earlier models and English conversation datasets; it does not establish current coding-agent performance. [Shaikh et al., Grounding Gaps in Language Model Generations, 2024 version](https://arxiv.org/html/2311.09144v2).

Research on repair across 12 languages finds that people target the trouble as specifically as they can and preserve understood material. Our application is to repair the missing term or premise instead of restarting the whole exchange. When the trouble is genuinely unknown, a broader diagnostic question can still be appropriate. [Dingemanse et al., 2015](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0136100).

Human-AI design guidance supports disambiguating uncertain goals, enabling correction, and explaining system behavior. Research on requesting further human input also distinguishes two causes: the input may be ambiguous, or the model may misunderstand a clear input. These support investigating before asserting that the user is wrong. Neither source supplies a ready-made contradiction detector or proves that this proposed evidence check works in coding conversations. The obligation to challenge a disputed claim openly comes from Peter. [Amershi et al., 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/), [Lemmer and Corso, 2022 version](https://arxiv.org/html/2110.10206v3).

Roberts's discourse model separates a partial answer, a complete answer, and information that does not address the current question. It also represents related subquestions without losing the earlier question. This provides a useful basis for handling mixed replies. Our deferred-topic record comes from Peter's requirement, not from the paper. The theory is idealized; it does not validate a rigid stack for every conversation or justify ignoring a user's deliberate change of direction. [Roberts, 2012](https://semprag.org/article/view/sp.5.6).

The preparation procedure is supported by the new [initiative research](research-initiative.md) and [decision-preparation research](research-decision-preparation.md). The TRAINS-95 assistant separates constructing and criticizing a route from the user's judgment of its delay. Recent research distinguishes missing user specification from model uncertainty and prepares compatible solutions before choosing a question. These support concrete proposals and targeted questions; they do not prove this skill's effectiveness. Cost-based rules that execute a guessed answer are not adopted. See [TRAINS-95](https://www.cs.rochester.edu/research/cisd/pubs/1996/ferguson-allen-miller-aips96.pdf), [Active Task Disambiguation](https://arxiv.org/abs/2502.04485), and [Structured Uncertainty guided Clarification](https://arxiv.org/html/2511.08798v2).

## Language and visual organization

**Language:** Use the project's established words and the reader's familiar community terms. Explain a necessary unfamiliar term where it is needed. Name the actor and action. Keep one main point in a sentence and one subject in a paragraph. Brevity serves meaning: keep a qualification that changes the decision, even when it makes the sentence longer. Consistent terminology and clear referents have direct support in Google's technical-writing guidance. [Google: Words](https://developers.google.com/tech-writing/one/words).

**Organization:** Orient the reader, give the necessary context in short paragraphs or real groups, then place the focused question next to its answers. GOV.UK's complex-question pattern uses this same broad sequence: a subject heading, explanatory text/lists/examples, then the specific question. It is a web-form pattern, so its HTML and screen-reader mechanics do not become universal dialog rules. [GOV.UK: Question pages](https://design-system.service.gov.uk/patterns/question-pages/#asking-complex-questions-without-using-hint-text).

**Options:** Describe outcomes the reader can distinguish and explain relevant consequences. When a question fails, change its framing or answer labels as needed, rather than adding more text to the same failing structure. GOV.UK reports a case where concrete answer labels clarified what counted as a second address. [GOV.UK: Designing good questions](https://www.gov.uk/service-manual/design/designing-good-questions).

W3C guidance supports clear words, focused text blocks, meaningful spacing, and visible benefits and consequences of choices. It is non-normative accessibility guidance, not a controlled trial of agent dialogs. [W3C: Making Content Usable](https://www.w3.org/TR/coga-usable/#keep-text-succinct-pattern).

**Defaults need their source identified.** One question at a time, a recommendation with its reason, and Peter's vocabulary priorities are product requirements. Exact line widths, word counts, glyphs, or group counts are formatting defaults or host constraints to verify. The reviewed sources do not establish those numbers as universal laws. GOV.UK's radio guidance even chooses a different ordering default and warns about preselection: its setting is collecting a user's answer, not advising on a programming decision. [GOV.UK: Radios](https://design-system.service.gov.uk/components/radios/).

## Changes to evaluate

These are proposed changes to the current artifact, not edits already made.

- **Put the full exchange in the main workflow.** The current body gives seven composition steps, then conditional pointers for failed questions and replies. Make interpreting every reply and selecting the next action explicit, including replies that match an option label. Existing detailed repair and reply references can still supply their conditional detail.
- **Prepare the decision instead of delegating the process.** Reporting an inconsistency and asking “How should we handle it?” leaves the agent's analysis undone. Research what is unknown, show the specific discrepancy, and propose the resolution or the bounded choice that remains.
- **Replace form-based assumptions with contextual interpretation.** The current reply reference says free text means rejection of the option set. Its notes-only section also attributes a specific attempted selection to the reader. Parse the returned structure, then determine what the actual words support. Preserve clear qualified decisions without asking for redundant confirmation.
- **Make the two clarity failures distinct.** An unclear question needs repair; an understood question with missing information needs investigation or a focused follow-up. A single label such as “failed question” can hide that difference.
- **Require evidence before dependent work continues.** A received answer may be incomplete, expose a larger question, or conflict with another source. Keep those gaps visible instead of silently supplying assumed answers or replacing the user's claims.
- **Preserve useful parts outside the current scope.** Treat the reply as potentially mixed. Record deferred material, explain the deferral, and return to the unresolved current question.
- **Align the description with intended use.** Its current exclusion says a wider job that pauses to ask should not use the skill. Peter intends automatic use for those exchanges while the wider workflow stays elsewhere. Review that exclusion without expanding the skill into project orchestration. Treat the wording mismatch as a candidate cause; verify actual selection rather than promising that a description edit alone fixes it.
- **Keep language and layout tied to the current question.** Preserve supporting context and use structure to expose it. Verify the current host's fields and rendering before prescribing a preview, newline, symbol, selection behavior, or reply format.
- **Make waiting explicit.** An unanswered question stays pending. The agent must not create a countdown, infer idle status from delay, or close the question on a timer. Host-controlled expiry is a separate limitation; it never supplies user consent.

The larger workflow decides **which question is next and when its workflow is complete**. The question skill handles **how that exchange is expressed and what its reply actually settles**. It returns answered parts, conditions, gaps, conflicts, and deferred topics to the larger workflow. Persistence uses the larger workflow's existing files: a glossary stays a glossary, and a deferred idea does not become an accepted ADR.

**wait-what supplies the repair trigger.** Its archived instruction requests context, plain language, and the project's words. It does not specify which repair to choose when the defect is combined scope, missing consequences, or incomplete information. Peter's mixed experience suggests testing a more specific repair loop; it does not establish the cause of those successes or failures. Preserve the pending question when a repair is requested, and respond to ordinary confusion as well as an explicit command. See context-wait-what.md. Changing that separate, general-message repair skill is outside this proposal.

Later evaluation should include these original, illustrative cases. They are proposed checks, not tests already run:

- An ordinary coding task reaches a real user-owned fork. The agent asks one clear question and applies the answer without taking over a larger interview workflow.
- Two inexpensive-to-reverse implementations preserve the agreed behavior. The agent makes a visible, reasoned choice without interrupting Peter or inventing an unprovided requirement.
- The user responds after a long delay. The agent has neither imposed a deadline nor dismissed the question; the actual reply still leads to the intended next step. Also test a host-originated expiry: the decision remains unanswered and dependent work stays pending.
- The agent discovers conflicting instructions. It investigates the relevant facts and prepares the specific resolution instead of asking the user to choose how it should investigate or align them. If evidence and existing decisions suffice, it proceeds within authorization without another question.

- A relevant question arises inside a programming task that never names the skill. The agent selects it before composing the exchange. A nearby task about writing a guide or rendering the dialog does not incorrectly select it.

- The user answers clearly with a condition. The agent carries the condition into the next step and does not ask the same decision again.
- The user asks what one term means. The agent explains that term and repairs the question without reopening settled parts.
- The reply states a goal but omits a needed choice. The agent identifies the missing choice and checks available evidence before asking again.
- The user asks the agent to research the issue. The agent researches instead of repeating a request for expert knowledge.
- The user rejects a premise or changes the goal. The agent updates the question instead of forcing the reply into the original choices.
- The tool returns no selection. The agent preserves any written constraints without inventing an answer or treating silence as consent.
- The user's answer exposes a larger gap than expected. The agent identifies the expanded gap and pauses dependent work instead of completing the answer from assumptions.
- A user claim conflicts with inspected code. The agent identifies the exact discrepancy and source, then resolves or discusses it openly. It neither agrees without evidence nor silently substitutes its own answer.
- A long reply contains useful future information but leaves the current question unanswered. The agent records the future topic, communicates the deferral, and asks about the specific missing piece. It neither discards the topic nor starts that work.

The outcome check is whether the next action fits the reply, preserves the user's meaning, and resolves the specific communication gap. A valid tool call or a shorter message is not enough evidence by itself. Actual execution and user review are still needed to establish that revised instructions improve the skill.
